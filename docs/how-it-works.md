# How it works

This walks through the code next to FIPS 203. The algorithm numbers are the standard's, and each function's comment names the one it implements.

Algorithms 3 and 4 (BitsToBytes, BytesToBits) don't appear as functions. The encoders shift bits in and out of an accumulator directly, least significant bit first, which is what the pair of them amounts to.

## Representations

**Polynomials** are `Uint16Array`s of 256 coefficients, always fully reduced to [0, q). With q = 3329, any product of two coefficients is below 2²⁴, so plain JavaScript numbers are exact and V8 keeps them on its int32 paths. Additions reduce with a compare and subtract; products use `%`.

**Keccak state** is 25 64-bit lanes stored as 50 32-bit halves in a `Uint32Array`, low word first. A `Uint8Array` view over the same buffer gives the byte order FIPS 202 expects, as long as the platform is little-endian. All current JavaScript platforms are, and the sponge throws on construction if not.

## Keccak

`keccak.ts` has two versions of Keccak-f[1600]:

- `keccakF1600Reference` follows the standard's steps (θ, ρ and π fused, χ, ι) as loops over index tables. It is the one to read.
- `keccakF1600`, which the sponge uses, is generated by `scripts/gen-keccak.mjs` as straight-line code: one local variable per state word, every index and rotation a constant. It is about four times faster. A test runs both on 200 pseudo-random states and requires identical output.

Neither copies the constants from a table. `keccak-constants.ts` computes the ρ offsets with FIPS 202 Algorithm 2 and the round constants with the rc LFSR of Algorithm 5. A test compares both with the published values.

The sponge absorbs whole blocks a 32-bit word at a time, squeezes with block copies, and pads bit by bit. Bit-level padding is needed only by the NIST vectors with messages that aren't a whole number of bytes. That case has a subtle edge, described in the devlog.

## The NTT

ML-KEM multiplies polynomials in R_q = Z_q[X]/(X²⁵⁶ + 1). 17 is a primitive 256th root of unity mod 3329, which is enough to split X²⁵⁶ + 1 into 128 factors X² − γᵢ with γᵢ = 17^(2·BitRev₇(i)+1), but not into 256 linear factors: that would need a 512th root. So:

- the NTT has 7 butterfly layers (lengths 128 down to 2), not 8, and its output is 128 pairs of coefficients, each a degree-1 polynomial mod its own X² − γᵢ;
- "multiplication in the NTT domain" multiplies those pairs: (a₀ + a₁X)(b₀ + b₁X) mod (X² − γ) = (a₀b₀ + a₁b₁γ) + (a₀b₁ + a₁b₀)X.

`ZETAS` and `GAMMAS` are computed at load time from 17 and checked against the first entries of FIPS 203 Appendix A. The inverse transform ends by multiplying by 3303 = 128⁻¹ mod q. Tests check that NTT⁻¹(NTT(f) ∘ NTT(g)) equals a schoolbook multiplication mod X²⁵⁶ + 1 on random inputs.

Each butterfly in a layer of length `len` pairs row j with row j XOR len. The explainer draws the dependency cones from this. Going back from one output, each layer adds the partner of every row, so after seven layers you reach 2⁷ = 128 inputs. Bit 0 of the index is never XORed, so they are exactly the inputs with the same parity.

## K-PKE and the KEM

K-PKE is the textbook Module-LWE scheme:

- **KeyGen**: (ρ, σ) = G(d ‖ k); Â[i][j] = SampleNTT(ρ ‖ j ‖ i); s, e ← CBD_η₁(PRF(σ, N)); t̂ = Â ∘ ŝ + ê. The public key is ByteEncode₁₂(t̂) ‖ ρ.
- **Encrypt(m, r)**: y, e₁, e₂ from PRF(r, N); u = NTT⁻¹(Âᵀ ∘ ŷ) + e₁; v = NTT⁻¹(t̂ᵀ ∘ ŷ) + e₂ + Decompress₁(m). The ciphertext is Compress_du(u) ‖ Compress_dv(v).
- **Decrypt**: w = v′ − NTT⁻¹(ŝᵀ ∘ NTT(u′)); m = Compress₁(w).

ML-KEM wraps K-PKE in a Fujisaki–Okamoto transform. Encapsulation derives the encryption randomness from the message: (K, r) = G(m ‖ H(ek)). Decapsulation can therefore re-run the encryption from the m′ it decrypted and compare the result with the ciphertext it received. If they differ, it returns K̄ = J(z ‖ c) instead of K′. That is _implicit rejection_: the caller always gets a key, and a forged ciphertext gives a key nobody else can compute.

Two details that are easy to miss:

- **The index order in SampleNTT's seed** is ρ ‖ j ‖ i, column first. With the order swapped you still have a working KEM, just not ML-KEM. Swapping it on purpose fails 18 of the 30 ML-KEM vector groups at once.
- **The byte k appended to d in G(d ‖ k)** is new in the final FIPS 203 (round-3 Kyber didn't have it). It makes the same seed expand to unrelated keys for different parameter sets. A test checks that the three ρ values differ.

## Why decryption works, in numbers

Write t = As + e, u = Aᵀy + e₁ + Δu, v = tᵀy + e₂ + μ + Δv, where Δu and Δv are the rounding errors of compression. Then

```
w = v′ − sᵀu′
  = (As + e)ᵀy + e₂ + μ + Δv − sᵀ(Aᵀy + e₁ + Δu)
  = μ + eᵀy − sᵀe₁ + e₂ + Δv − sᵀΔu
```

because (As)ᵀy = sᵀAᵀy. Everything but μ is small. Each coefficient of μ is 0 or 1665, and Compress₁ rounds w to the nearer of 0 and q/2. The bit comes out right as long as the noise is below q/4 ≈ 832 in absolute value.

The explainer's `noiseBreakdown` recomputes all five terms from the traced s, e, y, e₁, e₂, u, u′, v and v′, adds them up mod q, and compares the sum with the w that decryption actually produced. If any coefficient disagrees, the page shows "mismatch" instead of "exact". A unit test asserts "exact" for all three parameter sets.

## How the explainer gets its numbers

Every K-PKE and ML-KEM function takes an optional trace object:

```ts
const trace: KeyGenTrace = {};
mlKem768.keygenInternal(d, z, trace);
trace.aHat; // the 3 x 3 matrix, as computed
trace.sampling; // { candidates, rejected, bytes } from SampleNTT
```

When a trace is passed, the function copies its intermediates into it with `Object.assign` at the end. With no trace there is no extra work. The explainer (`apps/explainer/src/model.ts`) runs one traced exchange and derives everything else from it: histograms, compression errors, the noise breakdown, the NTT layers, tampering. The model has no DOM code, so `apps/explainer/test/model.test.ts` can check its numbers in Node. The sections only draw.

A few figures compute something independently and compare it with the trace:

- the SampleNTT candidates are read straight from SHAKE128(ρ ‖ 0 ‖ 0) and checked against Â[0][0];
- the NTT layers are recomputed one layer at a time from the library's `ZETAS`, and a test checks that the last one equals `ntt()`;
- the NTT check multiplies s[0] · Â[0][0] both ways and compares all 256 coefficients.

## Bit order in the NIST hash vectors

ACVP writes a bit string of n bits as hex, with the final partial byte left-aligned: its bits are in the high end. FIPS 202's convention (Appendix B.1) puts them in the low end. The library's `keccakBits` follows FIPS 202, and the test adapter shifts ACVP's last input byte right by 8 − (n mod 8) and the last output byte left by the same amount. The devlog has how that was worked out.
